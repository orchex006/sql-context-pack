# Proposal: 3.0.0 — Sensitive data must never reach an AI model

Status: **approved and built** on 2026-10-09 as requirement
[v1.1](../spec/design-spec-v1.1.md) and product 3.0.0. This page keeps the analysis and the
owner's decisions; v1.1 is authoritative where they differ (routine-body literals use visible
`[REDACTED:<CLASS>]` marks rather than fakes, and there is no `schema_only` mode).

## Objective

Sensitive data from a connected database must never reach an AI model's context, and
therefore can never be retained or used to train a model. Protection is done by the tool,
in code, before anything is returned. It must not depend on the model behaving well or on
the provider's data policy.

## Owner decisions (2026-10-09)

1. **Full data access, protected from the first byte.** No `schema_only` mode and no
   opt-in step. Every profile returns data, but sensitive values are protected by the tool
   from the very first result.
2. **When someone asks to see real sensitive values**, the AI never obtains them. Instead it
   returns a ready-to-run query, or step-by-step instructions, that the user runs
   themselves. Running it is the user's own implicit acceptance of seeing that data; the
   values go to the user, never to the model.
3. **No owner override file.** Do not add that complexity. Classification is built in.
4. **No `doctor` scan of 2.x exports.** Old exports are replaced as they are re-exported.
5. **Every sensitive value is marked**, with no exceptions.
6. **Auto-fake by the tool** for values whose shape matters: first name, surname, Thai
   national ID and similar. Faking is done in code, deterministically, never by the model.

## Findings that motivate it (analysis of 2.1.0, 2026-10-09)

1. Classification fails **open**: an unrecognised column is `PUBLIC`
   (`src/sqlctx/security/masking.py`, `DeterministicMaskingEngine.classify`), despite the
   module docstring claiming fail-closed.
2. Name rules are exact English words only. Measured on 2.1.0: `FIRST_NAME`, `LNAME`,
   `FARMER_NAME`, `PWD`, `TOKEN`, `ADDR`, `LATITUDE`, `REMARK` (free text containing a phone
   number and a name) all classify as `public`. `ID_CARD`, `DOB`, `BANK_ACC_NO` were masked
   only because the value happened to match the phone pattern.
3. `database_classification` exists but nothing supplies it; SQL Server
   `sys.sensitivity_classifications` is unused.
4. Export sample rows (`samples/`) use the same classifier and are written to disk where any
   agent can read them with ordinary file tools, bypassing MCP.
5. Routine bodies are scanned only for secret literals (`password=`, bearer, private keys),
   not for PII literals.
6. Column descriptions from `sys.extended_properties` are exported unscanned.
7. Masked values can be inferred through query predicates (`WHERE`, `LIKE`, `LEN`,
   `HASHBYTES`, `COUNT` on a sensitive column).

## Rules

1. **Fail-closed.** A column is returned as-is only when the tool classifies it public with
   confidence. Unknown column → treated as sensitive. Unknown lineage → `[REDACTED]`
   (already true). System catalog views (`INFORMATION_SCHEMA.*`, `sys.*` metadata) are public
   so schema discovery keeps working.
2. **Classification sources, in priority order:** `sys.sensitivity_classifications` →
   built-in rules → default *sensitive*. There is no override file.
3. **Built-in Thai/AgriMap rules**: `*name`, `fname`, `lname`, `tel`, `mobile`, `addr`,
   `pid`, `id_card`, `citizen*`, `dob`, `birth*`, `pwd`, `pass*`, `token`, `lat`, `lon*`,
   `geom`, `bank*`, `acc*_no`, plus value patterns: 13-digit Thai ID with checksum, Thai
   mobile numbers, email.
4. **Treatment by class**, all applied by the tool:

   | Class | Treatment | Example output |
   | --- | --- | --- |
   | Password, secret, token, key, biometric | redact | `[REDACTED]` |
   | First name, surname, full name | **fake** from built-in Thai name lists | `สมศรี` |
   | Thai national ID | **fake** 13 digits with a valid checksum | `3-1009-01234-56-1` |
   | Phone | **fake** same format | `08x-xxx-xxxx` shaped |
   | Email | **fake** | `user_k3f9@example.invalid` |
   | Bank account, card | **fake** same length, invalid issuer | |
   | Address, precise location, date of birth | generalize | `[ADDRESS]`, district only, year only |
   | Free text (`remark`, `note`, `desc*`, unknown `nvarchar(max)`) | scan, fake detected PII inside, else redact | |

   Fakes are deterministic within one query or one export (the same real value always gets
   the same fake, so joins and grouping still make sense) and use a random key that is never
   persisted, so a fake cannot be reversed.
5. **Marking is complete.** Every non-public column carries its class and treatment in the
   result metadata (`sensitivity`, `treatment: public|fake|alias|generalize|redact`), and the
   Markdown header marks it, e.g. `FIRST_NAME ⟨FAKE:PERSONAL_NAME⟩`. A faked value must never
   be presentable as real; the model is instructed to say so whenever it quotes one.
6. **Inference guard.** The query validator rejects sensitive columns in `WHERE`, `JOIN ON`,
   `GROUP BY`, `ORDER BY`, aggregates and functions, not only in the projection. A rejection
   returns the reveal handoff instead of a bare error.
7. **Reveal handoff.** When a request needs real sensitive values (including a guard
   rejection), the tool returns `{"reveal_handoff": {...}}` with a ready-to-run SELECT and the
   steps for the user to run it themselves (e.g. SSMS or the owner CLI
   `sqlctx query --reveal`). The tool never executes it on the model's behalf, and the owner
   CLI output is written to the user's terminal, never into an MCP payload.
8. **Every bound is reported** (AGENTS.md §10.6): counts of redacted, faked and generalized
   values per column.

## Model training

No code can control what a provider does with data it receives; the only guarantee is that
sensitive data is never sent. Rules 1–7 provide that guarantee. As a second layer, the
release notes will state that hosts must run under a plan whose terms exclude training on
inputs (commercial/API, Team or Enterprise plans, or a consumer account with training
opted out).

## Why this is 3.0.0

`sqlctx_query_data` output changes meaning: values that 2.x returned become fake, generalized
or `[REDACTED]`; result metadata gains marking fields; some queries 2.x accepted are rejected
with a reveal handoff. These are contract breaks under AGENTS.md §3.4.
